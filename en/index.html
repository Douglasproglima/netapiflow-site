Live request flow visualizer · ASP.NET Core

NETAPIFLOW

Complex integrations. Linear flows.

A route goes slow on a random Tuesday afternoon. Nobody knows if the problem is the database, an external service, or a branch of logic that never even ran. NetApiFlow shows the exact path of every HTTP request inside your own API, live, from the endpoint to the SQL command. Duration per step, where it failed, and what should have run and never did.

Engineering manifesto

Four principles that do not bend

01

Strongly Typed (.NET)

Native DI and ASP.NET Core middleware integration, with typed tracking events. Marking a step with Flow.Step uses no reflection. The optional proxy of AddFlowTracked, DecorateFlowTracked and TrackFlowByConvention does.

02

Active Diagnosis

Shows where the failure began, what got slow, and what never executed. State is always color plus icon plus text, never just color.

03

Fluent Configuration

Two NuGet packages, a few lines of code, one local URL. Filters by route, composed in a fluent API.

04

Measured Overhead

Asynchronous collection, toggleable per environment. Measured on 0.6.0 with BenchmarkDotNet, on .NET 8 and .NET 10, on one laptop that was also running other programs, so read it as an order of magnitude. Tracing adds about 13 to 14 microseconds to a request with no steps marked, and about 16 to 23 with four nested steps. With Enabled = false it adds 0.4 to 1.7. The benchmark and its method are published.

What it does

Three pillars

Live

Live Tracking

Real time graph of the request path. Endpoint, then Handler, then Services, then Repositories, then SQL. Works with Clean Architecture, Vertical Slices and MediatR.

Diagnose

Failure & Latency Diagnosis

Duration per step, exception origin, slow steps above threshold, and what never executed, without opening a debugger or mining logs.

Replay

Telemetry & Replay

Execution history with trace ID, filter by route, and a replay timeline with speed control to see exactly what happened.

Beyond the basics

The rest of the package

Tracing the request is just the start. The rest of the ecosystem helps you find a problem before it's an incident, and bring the trace to where you already work.

MCP

Ready for an AI agent

Your own API exposes an MCP server: an agent lists recent traces, fetches one by id, and reads per-component statistics, with no hand-written REST client.

OTLP

Interops with your stack

Exports the same trace to Jaeger, Tempo, Aspire Dashboard, Honeycomb, or any OpenTelemetry-compatible collector. Native Npgsql and HttpClient ingestion, no duplicate spans.

Insights

Sees what a single run can't

Automatic N+1 detection on the graph, an architecture map built from hundreds of real executions, and an aggregated view of the slowest and most error-prone routes.

Runner

Test a route without leaving the dashboard

Builds the form straight from your own API's OpenAPI document and fires a real request. On a protected route, paste the token once: the right header is applied automatically to every request, no copy-pasting it again.

Testing

Asserts on the flow, in your integration tests

NetApiFlow.Testing turns "this endpoint must not hit the database more than three times" into a test that fails when it does, instead of something you notice by eye in the dashboard. It pulls in no assertion library.

And more: side-by-side diff between two executions, a trace exported as a file to take anywhere, smart sampling that keeps only what matters, log/exception correlation per step, and a deploy marker on the history timeline to correlate an incident with someone else's deploy.

Get started

Install two packages, add a few lines

No separate service to deploy. The dashboard ships embedded in the NetApiFlow.Dashboard package and runs next to your API.

Terminalin a project made with dotnet new webapi
dotnet add package NetApiFlow
dotnet add package NetApiFlow.Dashboard

Update the NetApiFlow packages together. Each package asks for the core at exactly its own version. If they do not match, NuGet says so when it restores: NU1605 (an error) when the core is older than a package needs, NU1608 (a warning) when it is newer.

Then put this in Program.cs. On .NET 10, AddOpenApi and MapOpenApi are the template's own, so keep them: the Runner lists your endpoints from your app's OpenAPI document. The /hello line stands for your own endpoints.

Program.cs.NET 10
using NetApiFlow;
using NetApiFlow.Dashboard;
using NetApiFlow.Dashboard.Endpoints;

var builder = WebApplication.CreateBuilder(args);
builder.Services.AddOpenApi();
builder.Services.AddNetApiFlow();
builder.Services.AddNetApiFlowDashboard();

var app = builder.Build();
if (app.Environment.IsDevelopment())
{
    app.MapOpenApi();
}

app.MapNetApiFlowDashboard(); // mounted at /flow by default

app.MapGet("/hello", () => "Hello");

app.Run();

MVC controllers and Minimal API endpoints become a step on their own, with nothing to mark. A request that matches no route is still listed, with zero steps. To draw the layers under the endpoint too, see Marking forms in the README.

On .NET 8, the dotnet new webapi template has no AddOpenApi and no MapOpenApi. It uses Swashbuckle, so pasting those two lines gives CS1061. Keep what the template generated, leave the two lines out, and point the Runner at the document Swashbuckle serves:

Program.cs.NET 8
builder.Services.AddNetApiFlow(options => options.OpenApiDocumentPath = "/swagger/v1/swagger.json");

Without that path the Runner says it could not load the OpenAPI document and lists no endpoint. Nothing else changes.
