NETAPIFLOW

Integrações complexas. Fluxos lineares.

Uma rota fica lenta numa terça à tarde. Ninguém sabe se o problema é no banco, num serviço externo, ou numa lógica que nem chegou a rodar. O NetApiFlow mostra o caminho de cada requisição HTTP dentro da sua própria API, ao vivo, do endpoint ao comando SQL. Duração de cada etapa, onde falhou, e o que deveria ter executado e nunca executou.

Manifesto de engenharia

Quatro princípios não negociáveis

01

Tipagem forte (.NET)

Integração nativa com DI e middleware do ASP.NET Core, com eventos de rastreamento tipados. Marcar uma etapa com Flow.Step ou num endpoint não usa reflexão. O proxy opcional do AddFlowTracked, do DecorateFlowTracked e do TrackFlowByConvention usa.

02

Diagnóstico ativo

Mostra onde a falha começou, o que ficou lento e o que nunca executou. Estado sempre com cor, ícone e texto. Nunca só cor.

03

Configuração fluente

Dois pacotes NuGet, poucas linhas de código, uma URL local. Filtro por rota, composto numa API fluente.

04

Overhead medido

Coleta assíncrona e desligável por ambiente. Medido na 0.6.0 com BenchmarkDotNet, no .NET 8 e no .NET 10, num notebook que também rodava outros programas, então leia como ordem de grandeza. O rastreamento soma cerca de 13 a 14 microssegundos a uma requisição sem nenhuma etapa marcada, e cerca de 16 a 23 com quatro etapas aninhadas. Com Enabled = false soma de 0,4 a 1,7. O benchmark publicado, não estimado.

O que ele faz

Três pilares

Live

Rastreamento ao vivo

Grafo em tempo real do caminho da requisição. Endpoint, depois Handler, depois Services, depois Repositories, depois SQL. Funciona com Clean Architecture, Vertical Slices e MediatR.

Diagnose

Diagnóstico de falha e lentidão

Duração por etapa, ponto de origem da exceção, etapas lentas acima do limite e o que deixou de executar, sem abrir debugger nem garimpar log.

Replay

Telemetria e replay

Histórico de execuções com trace ID, filtro por rota, e timeline de replay com controle de velocidade para rever exatamente o que aconteceu.

Além do essencial

O resto do pacote

Rastrear a requisição é só o começo. O resto do ecossistema ajuda a achar problema antes do incidente, e a levar o trace pra onde você já trabalha.

MCP

Pronto pra um agente de IA

Sua própria API expõe um servidor MCP: um agente lista traces recentes, busca um por id e lê estatística por componente, sem nenhum cliente REST escrito à mão.

OTLP

Interopera com seu stack

Exporta o mesmo trace pro Jaeger, Tempo, Aspire Dashboard, Honeycomb ou qualquer coletor compatível com OpenTelemetry. Ingestão nativa de Npgsql e HttpClient, sem duplicar span.

Insights

Acha o que não dá pra ver numa execução só

Detector de N+1 automático no grafo, mapa de arquitetura construído a partir de centenas de execuções reais, e uma visão agregada das rotas mais lentas e com mais erro.

Runner

Testa uma rota sem sair do dashboard

Monta o formulário direto do documento OpenAPI da sua própria API e dispara a requisição de verdade. Numa rota protegida, cole o token uma vez: o header certo é aplicado automaticamente em cada requisição, sem copiar e colar de novo.

Testes

Asserções sobre o fluxo nos seus testes de integração

O NetApiFlow.Testing transforma "este endpoint não pode chamar o banco mais de três vezes" num teste que falha quando chama, em vez de algo que você nota a olho no dashboard. Não puxa nenhuma biblioteca de asserção.

E mais: diff entre duas execuções lado a lado, trace exportado como arquivo pra levar pra qualquer lugar, sampling inteligente pra reter só o que importa, log/exceção correlacionados por etapa, e um marco de deploy na linha do tempo do histórico, pra correlacionar um incidente com um deploy de outra pessoa.

Para começar

Instale dois pacotes, adicione poucas linhas

Nenhum serviço separado para fazer deploy. O dashboard vem embutido no pacote NetApiFlow.Dashboard e roda junto da sua API.

Terminalnum projeto criado com dotnet new webapi
dotnet add package NetApiFlow
dotnet add package NetApiFlow.Dashboard

Atualize os pacotes NetApiFlow juntos. Cada pacote pede o núcleo exatamente na sua própria versão. Se não combinarem, o NuGet avisa na hora do restore: NU1605 (um erro) quando o núcleo é mais velho do que o pacote precisa, NU1608 (um aviso) quando é mais novo.

Depois coloque isto no Program.cs. No .NET 10, AddOpenApi e MapOpenApi são do próprio modelo, então mantenha as duas: o Runner lista os seus endpoints a partir do documento OpenAPI da sua aplicação. A linha /hello representa os seus próprios endpoints.

Program.cs.NET 10
using NetApiFlow;
using NetApiFlow.Dashboard;
using NetApiFlow.Dashboard.Endpoints;

var builder = WebApplication.CreateBuilder(args);
builder.Services.AddOpenApi();
builder.Services.AddNetApiFlow();
builder.Services.AddNetApiFlowDashboard();

var app = builder.Build();
if (app.Environment.IsDevelopment())
{
    app.MapOpenApi();
}

app.MapNetApiFlowDashboard(); // montado em /flow por padrão

app.MapGet("/hello", () => "Hello");

app.Run();

Controllers MVC e endpoints de Minimal API viram uma etapa sozinhos, sem nada para marcar. Uma requisição que não casa com nenhuma rota continua listada, com zero etapas. Para desenhar também as camadas abaixo do endpoint, veja Formas de marcar etapas no README.

No .NET 8, o modelo dotnet new webapi não tem AddOpenApi nem MapOpenApi. Ele usa o Swashbuckle, então colar essas duas linhas dá CS1061. Mantenha o que o modelo gerou, deixe as duas linhas de fora e aponte o Runner para o documento que o Swashbuckle serve:

Program.cs.NET 8
builder.Services.AddNetApiFlow(options => options.OpenApiDocumentPath = "/swagger/v1/swagger.json");

Sem esse caminho, o Runner diz que não conseguiu carregar o documento OpenAPI e não lista nenhum endpoint. Nada mais muda.

Toda etapa, cor, ícone e texto

Estado nunca é só cor. Continua legível em escala de cinza, para quem tem daltonismo, e numa impressão em preto e branco.
